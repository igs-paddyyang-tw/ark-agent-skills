# ark-mobile-adb v2.1

## 0. 一句話

那份分析的結論是對的：瓶頸不在 adb，在「每步截圖給 AI 看」這個 loop。v2.0 已經把方向定成「AI 只看不判、gamepack 放知識」，但**還沒有給「執行期完全不用眼」的工具**——v2.1 補的就是這一段：按鍵精靈式 macro（錄製 → 建表 → 重放 → 檢查點）、座標唯一基準、單進程批次、自動重連，並把它們寫成 SOP 與參考知識，讓 agent 和人都照同一套走。

## 1. v2.0 對六個根因的覆蓋，與 v2.1 補的洞

| 根因（分析文件） | v2.0 已有 | 洞 | v2.1 |
|---|---|---|---|
| R1 每步一個 Python 進程（冷啟 2–3s） | 無 | 每個 tap 都開一次 Python | `batch --file`（多行子命令一個進程）、`shell-chain`（一次 adb shell 串多指令，實測省 78%）、`aiqa_macro.py replay`（整支腳本一個進程） |
| R2 每步一次視覺分析（最貴） | gamepack 模板比對定位、`wait-stable`；aiqa_run 只在 read / ask 問 AI | 導航仍會截圖偵測畫面；沒有「純重放」模式；沒有找色 | **macro DSL**：執行期零 LLM；`checkpoint`（模板）/ `assert_pixel` / `wait_pixel`（找色，毫秒級）；`pixel` 指令建找色點 |
| R3 座標與截圖尺寸耦合 | pack 解析度必須 = wm size | 縮圖沒有帶 scale；agent 照樣可能拿縮圖座標去點 | `thumb` 強制寫 `.meta.json`（scale + 警語）；`to-device X Y --basis WxH`；`tap --basis`；macro lint `MC-COORD` 抓超界座標；`references/coordinate-basis.md` 一張表 |
| R4 Unity 無 UI 樹 | 模板 + xy 退路 | — | 同 v2.0；補「找色」作為第三種錨點（最快） |
| R5 連線不穩 + 固定 sleep | `wait-stable` | adb offline 只會報錯 | `adb()` 包裝層偵測 offline / not found → 依 `.ark-mobile.json` 的 `"connect"` 自動 `adb connect` 一次再重試（最多 3 次 / 進程）；`wait_pixel` / `wait_screen` 取代 sleep |
| R6 Python 冷啟異常慢 | 無 | — | 系統層只能寫 SOP：Defender 排除 Python / platform-tools / 專案目錄；用 batch / macro 讓一輪只付一次冷啟（`references/performance-tuning.md`） |

結論：**v2.0 有骨架沒有腳本層；v2.1 補腳本層與 SOP**。分析文件 §5 的七條優化方向，一到六在 v2.1 有對應指令，第七條是系統設定寫進 SOP。

## 2. 按鍵精靈式腳本開發模式

```
探勘(眼) → 建表(眼) → 錄製/編寫(手) → lint(機) → dry-run(機) → 加檢查點(眼+機) → 實跑量測(機) → 版本化(機)
```

| 階段 | 指令 | 產物 |
|---|---|---|
| 探勘 | `doctor` `screen-size` `screenshot` `ui-dump` | 裝置尺寸截圖；確認 Unity |
| 建表 | `crop --zoom 1` 裁錨點模板、`pixel --xy` 記找色點 → 寫 pack `screens / buttons / rois` → `aiqa_pack.py lint` | gamepack |
| 錄製 | 人在 BlueStacks 操作一次，同時 `aiqa_macro.py record --game g --machine m --out m.yaml --duration 90`（`getevent -lt` → 自動換算成 wm size 座標、間隔 ≥ 0.8s 自動插 `wait_stable`） | macro 草稿 |
| 編寫 | `[x,y]` → `btn:<name>`（改版只改 pack）；`sleep` → `wait_stable / wait_pixel / wait_screen`；彈窗 → `if_screen`；重複 → `loop` | macro.yaml |
| lint | `aiqa_macro.py lint`：步驟合法、target 在 pack、解析度一致、座標不超界、至少一個檢查點（`MC-BLIND`） | exit 0 / 3 |
| dry-run | `replay --dry-run`（不點擊只走 locate / 檢查點）或 `replay --backend fake`（demo-slot 驗 DSL） | summary.json |
| 檢查點 | 每個「點下去之後應該變成什麼」放 `checkpoint` / `assert_pixel`；數值放 `ocr ... expect` | 有檢查點的 macro |
| 量測 | `replay --backend adb` → summary.json `elapsed_s / steps / shots`；與視覺驅動各跑三次取中位數 | 加速比紀錄 |
| 版本化 | macro 與 pack 同 commit，綁 app 版本與解析度 | git |

**分工**：macro 管「走到那裡」（確定性、零 LLM），checklist 斷言管「對不對」（oracle 判定，AI 只在 read / ask）。checklist 用 `{do: macro, name, vars}` 呼叫；macro 檢查點失敗 → 該項 BLOCK 附截圖，不會假 PASS。

## 3. DSL（見 `references/macro-sop.md` §1）

`tap`（`btn:<name>` 或 `[x,y]`）、`swipe`、`key`、`sleep`、`wait_stable`、`wait_screen`、`wait_pixel`、`checkpoint`、`assert_pixel`、`if_screen`、`loop`、`ocr`（含 `expect`）、`shot`、`restart_app`、`net`、`note`。`explain` 把 macro 渲染成編號 SOP，測試員可照做、AI 可當參考。
