# 教學引擎（teaching engine）

蒸餾自 [hung-yi-lee-skill](https://github.com/voidful/hung-yi-lee-skill)（逐字稿反推的教學結構 + 本人訪談校準），
去掉個人語癖與人格模仿，只保留「讓人學會」的結構性招式。寫每一章前讀一次；寫完用最後的自評清單過一次。

## 為什麼教材不是文件

| 文件 | 教材 |
|---|---|
| 從系統結構出發：模組 A、模組 B、模組 C | 從讀者遇到的問題出發：你想做 X，第一步會卡在哪 |
| 給定義，再給用法 | 先給問題，讀者會先想到的做法，它的極限，「怎麼辦？」，方法登場 |
| 列出所有選項 | 只講這章要學會的那一個能力，其餘標「這章不講」 |
| 讀完知道「有這個東西」 | 讀完能做一件事，且記得一句話 |

判準：把章節內容用「這是什麼」開頭的句子全部刪掉，剩下的還能不能教會人？不能 → 這是文件，重寫。

## 三條鐵律（本人訪談確認，優先級最高）

1. **有脈絡，不流水帳**
   概念之間要有因果線：「因為做法 A 在情境 S 撞牆，所以才有 B；B 解決了 S 但引入了 T，所以有 C。」
   一章如果能把段落任意調換順序而不影響閱讀，就是流水帳。
2. **每章有 punchline**
   一句讀者一週後還記得的話，它承載整章的核心，不是裝飾。先寫 punchline 再寫內文；寫在 frontmatter，也是回顧的第一句。
   例：「一個 worker 一個判準；判準不同就拆。」「放行決策只有人能下。」「lint 過了才算完成，自評不算。」
3. **教方法的來歷，不只教方法**
   不要寫「team-design 是一個用來設計編制的工具」。要寫：「你想建一個助理，第一個念頭是直接寫 team.yaml。寫到第三個 worker 你會發現分不清誰該管什麼。怎麼辦？所以才需要先訪談出編制——這就是 team-design 做的事。」

第四條同等重要：**相關性先於基礎**。開頭要讓讀者覺得「這跟我有關、我馬上能用」，原理放在後面。從「基礎概念」開頭是失去讀者的預設方式。

## 章節的節奏（對應七段結構）

### 1. 這章要解決的問題（先讓問題痛）
- 描述一個讀者會真的遇到的具體情境，用他的專案名、他的工具、他會下的指令
- 說出讀者第一個會想到的做法
- 指出它在哪裡不夠（具體現象，不是抽象缺點）
- 以「怎麼辦？」收尾 —— 這個問號是方法登場的門

### 2. 路線圖
- 「這章分三步：先…，接著…，最後…」
- 讀者知道要走幾步，就能放鬆跟上；每步結束時有「好，這是第一步」的標記

### 3. 內文（直覺—形式化循環）
每個新概念跑一輪：

1. **直覺例子**：先描述它「做什麼」，不用術語（比如說…／假設你今天…）
2. **修辭問句**：「那這個東西叫什麼？」「為什麼要這樣做？」
3. **命名儀式**：「這個東西我們叫做 X」——先描述功能再給名字，讀者才有記憶錨
4. **形式定義**：精確的規則、指令、參數
5. **第二個例子**：不同情境，證明規則不是只對一個例子成立
6. **一句話收**：「簡單來說，X 就是…」

複雜概念用**策略性簡化**：先拿掉一個維度（先只看一個 worker、先不管 admin），建立直覺後再加回來。
概念有多層時用**逐步加難螺旋**：最簡版 → 指出限制 → 加一層 → 重複；每加一層先回顧上一層。
需要推導或深入時加**安全網**：「以下比較細，看不懂可以跳過，只要記得結論是…」，結論在進入前與離開後各講一次。

### 4. 常見誤解
- 「大家通常會以為…」→ 停一拍 →「但其實…」→ 為什麼錯 → 正確理解 → 一句記憶點
- 批評做法，不批評持有這個想法的人；用「大家通常」，不用「你如果這樣想就錯了」
- 每個主要概念至少一個誤解

### 5. 動手做
- 讀者能立刻執行的東西：一段指令、一個腳本、一張檢核表、一個要填的 yaml
- 附「你應該看到什麼」與「如果看到 X，代表 Y」
- 動手做的產出，最好就是這本書想累積的「腳本」或「知識庫條目」——讀者做完，圖書館就多一本館藏

### 6. 重點回顧
- 最多三句，短句，第一句是 punchline
- 「如果你只記得一件事，記得…」

### 7. 下一章
- 一句話橋接：「這章你有了編制，但每個 agent 還是『一個專業的 X』這種空話。下一章給它人格。」

## 招式速查

| 招式 | 什麼時候用 | 樣子 |
|---|---|---|
| 一言以蔽之 | 每章開頭、每個大概念 | 「一言以蔽之，role-profile 其實就是把『你是誰、絕不做什麼』寫成資料而已。」 |
| 黑盒先於內部 | 介紹任何工具/腳本 | 先講輸入→輸出→它在保證什麼，再打開看怎麼做 |
| 你可能會想說 | 讀者可能卡住的地方 | `> [!ASK]` 主動說出讀者心裡的問題，然後回答 |
| 規模有感 | 出現數字 | 「17 個 skill」→「照著做一輪約 40 分鐘，第二次 15 分鐘」 |
| 誠實邊界 | 簡化的地方、沒定論的地方 | 「這章先這樣理解就夠；細節在第 5 章」「這件事目前沒有標準答案」 |
| 類比 | 抽象結構、3 段以上純技術 | 用讀者共享的參照（他的日常工具、遊戲、工作流程）；類比要說明「到這裡為止不再成立」 |
| 反高潮 | 拆完一個機制 | 「然後呢？然後就結束了。就這麼簡單，沒有隱藏的魔法。」 |
| 反 hype | 出現聽起來很厲害的詞 | 「所謂 X，其實就是 Y 而已。」 |
| 引導發現 | 想讓讀者自己得到結論 | 「你會發現，三個 worker 的『完成』定義其實不一樣……」 |
| 號稱 | 轉述未驗證的主張 | 「號稱可以自動同步」——標出這是別人說的 |

## 寫給 AI 讀者的規則（與人類讀者並行）

章節會被 wiki 切塊檢索，所以：

- 每個 `##` 段落開頭第一句是該段結論
- 不跨段指涉（禁「如上所述」），主詞寫全名
- 術語第一次出現時同時給中英文與一句白話（讓檢索能命中兩種寫法）
- 主張附 sources 路徑；推測標 `confidence: low`
- `[!TIP]`/`[!MYTH]`/`[!TRY]` 標記讓下游 agent 能只抽「白話定義」「常見錯誤」「可執行步驟」

## 自評清單（寫完每章跑一次；lint 只能查結構，這裡查教學品質）

### 必要（全部要過）
- [ ] 開頭是讀者會遇到的具體問題，不是定義
- [ ] 每個術語出現前有直覺例子；出現後有第二個例子
- [ ] 有一條清楚的因果線貫穿全章（能說出「因為…所以…」）
- [ ] punchline 一句，回顧第一句就是它
- [ ] 至少一個 `[!ASK]` 與一個 `[!MYTH]`
- [ ] 動手做的東西讀者真的能執行，並知道成功長什麼樣
- [ ] 簡化的地方有標邊界
- [ ] 沒有對特定人事物的負面評價

### 建議（至少三項）
- [ ] 一個讓讀者「有感」的規模比較
- [ ] 一個類比，且說明類比的失效點
- [ ] 一次反 hype（其實就是…而已）或反高潮（就結束了）
- [ ] 一次引導發現（你會發現…）
- [ ] 一處誠實的「目前沒定論」或「要看情況」
- [ ] 例子用讀者自己的專案/工具名

### 不合格（任一即重寫）
- ❌ 術語先於例子
- ❌ 段落可任意換序（流水帳）
- ❌ 只給方法不給來歷（「X 是一個用來…的工具」開頭）
- ❌ 沒有動手做，或動手做無法執行
- ❌ 回顧超過三句、或沒有 punchline
- ❌ 權威口吻（「你們應該知道」「這是基本的」）
- ❌ 內容能一字不改地當「規格文件」用 —— 那它就不是教材
