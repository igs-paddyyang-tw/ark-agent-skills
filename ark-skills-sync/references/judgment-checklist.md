# 判準檢查表 —— 動這個庫之前先過一遍

> 來源：2026-09-14~15 兩天、四批工作、10 個 repo 的實際踩點。
> 每一條後面的例子都是**真的發生過**，不是假想。
> 用法：不是逐條打勾，是**動手前掃一眼有沒有哪條正在發生**。

## A. 加守門之前

### A-1~A-4 → **已上移到根 `AGENTS.md`**（`## 新加的檢查要先反證「它會不會紅」`）

反證兩個方向、先看「掃到幾個」合不合理、範圍空要明說跳過 —— 三條都不限於這個庫。
**這裡不留第二份**，只留本庫踩到的實例當佐證：

| 條 | 本庫實例 |
|---|---|
| 反證會不會紅 | `orphan-asset` 第二版把最上層 `references`/`assets` 也算「提到」，而幾乎每份 SKILL.md 都有這個字 → 塞 `ghost.md` 進去**也不紅**。是刻意去塞才發現 |
| 先看掃到幾個 | 驗矩陣的腳本回報「引用 **1 個** · 斷鏈 0 ✅」——`MATRIX` 是 AnnAssign，只判 `ast.Assign` 整個矩陣掃不到 |
| 範圍空要明說 | `check_consumers.py` 消費端根目錄不存在時若靜默回 0，就成了「掃描回報成功而其實什麼都沒掃」 |
| 訊息要可行動 | 測試檔名重複的守門**直接印出建議的唯一檔名** —— 只說「重複了」的話，下一個人還要自己想一個，而通常會想出另一個通用名 |

### A-3.5　「反證會紅」只證明測試擋得住改動，**不證明擋的方向是對的**

> 實例：`92646c3` 把 `agent.json` 的 `file://../../…` 改成 `file://…`，
> 附一條反向測試斷言「不得有 `../..`」，commit 寫「反證會紅」。
> 但 `file://` 的基準是**放這個 json 的目錄**（`.kiro/agents/`），
> 原本的 `../../` 才是對的 —— 反證擋住了正確的那個方向。

**方向要用外部證據定**，不能用自己的測試自我背書：
去看**實際在跑的部署**怎麼寫、去看有沒有文件記過這個陷阱。
（那次兩個在跑的部署與專案 CLAUDE.md 都站在 `../../` 這邊。）

💡 推論式的理由（「假設兩層深」）最容易反 —— 動手前先把它**算一遍**：
`../../` 從 `<X>/.kiro/agents/` 出發是回到 `<X>/`，與 `<X>` 有幾層無關。

### A-4　要求「補一個章節」之前，先確認那資訊是不是已經在別處是唯一真相

> 實例：原計畫強制每個 SKILL.md 有 `## 觸發條件`。實測 18 個缺章節的 skill，
> **18/18 的 description 早就有觸發詞**，而 agent 路由讀的就是 description。
> 強制章節＝再生一份同樣的真相，正是這兩天一直在修的漂移形狀。→ **否決原案。**

### A-5　沒有鄰居就不要寫邊界宣告

填充文字會稀釋真正的邊界。**指名「會被誤觸的那一個」，指不出來就不要寫。**
（31 個缺邊界的 skill，補了 23、刻意不補 8。）

### A-6　豁免清單的終點是歸零，不是「維持一個好清單」

清單存在的期間唯一價值是「讓紅燈可分批」，代價是「有東西被蓋住」。

## B. 刪東西之前：三段判準

**只做第①段會靜默掉能力，而所有指標都正常。**

| 段 | 問什麼 | 依據 | 漏掉的代價 |
|:--:|---|---|---|
| ① | 該不該刪 | 上游 git 歷史**有過**＝殘留；**沒有過**＝專案自建 | 差點刪掉 74 個別人寫的 skill |
| ② | 接手者是誰 | `metadata.replaces` → 移除 commit 的**箭頭／併入式**宣告 → 推不出來就**明說不確定** | 1 個 agent 靜默失去匯出能力 |
| ③ | **這個 agent 該不該有接手者** | 接手者是 scaffolder 而這個 agent 是職人／管家 → **是刪不是換** | 把清掉的注入量又加回去 |

### B-1　「上游沒有」不等於「該刪」

要分清「曾經有、後來移除」與「從來就不是上游的東西」。
**查歷史才分得出來，查現況只會看到同一種樣子。**

### B-2　第②段不猜

批次移除的 commit 會同行並列好幾個名字，靠「同行出現」推斷會得到錯的接手者。

> 實例：`ark-executive-assistant` 被推成 `ark-community-ops` —— 兩者只是同批被刪。
> **猜錯的接手者比「不知道」更糟**：照著補裝會裝進一個同樣不存在的東西。

自己做的整併請回頭補 `replaces:`，那是唯一權威來源。

### B-3　上游做移除，就要由上游負責掃消費端

「消費端自己會檢查」在多 repo／多機器情境下等於沒有檢查 ——
消費端的 `--check` 本來就會擋，問題是**沒有人會去跑它**。

### B-4　傳染力最強的那個面是「出貨的範例包」

> 實例：三個真實消費端的矩陣都改了，**唯獨 `examples/` 的範例沒改**，
> 而範例是新專案照抄的東西。那次是靠某個消費端剛好有一份複本才反向命中。

## C. 兩份真相的形狀（這兩天 7 個缺陷全是這一類）

### C-1　產生器與驗證器共用同一個錯誤假設時，驗證等於互相背書

> 實例：`build_kiro` 用 `role` 決定 `.kiro/` 落點（執行期其實看 `working_directory`），
> 而 `validate_kiro()` **抄了同一條錯規則**去找檔案 → 找得到、回報通過。

作法：驗證要**直接讀來源真相**（`team.yaml`），不要經過同一套推導。

### C-2　一致但都錯，是「對不上」的另一種形態

只比對兩邊的守門看不到它。要多問一句「**產出來有沒有人用**」。

> 實例：`SlotMechanics`／`VibeScore` 三份文件都列、scaffold 也產了，
> 而**產出的程式碼一個都沒 import 它們** —— 每個新專案都多兩個死檔。

### C-3　註解不能長得像它要描述的東西

> 實例：`team.yaml.tpl` 第 2 行註解寫著 `{instances_block}` 字面 →
> 照 SKILL 說的做字串替換會把註解一起換掉，產出的 YAML 第 2 行就 parse 失敗。
> 我在補另一處註解時又犯一次（寫出數字字面，絆倒自己的手寫統計守門）。

### C-4　手寫統計必定漂

產生器只保證自己產的那段。手寫的數字要嘛拿掉，要嘛另外有東西在驗。

### C-5　不需要依賴的路徑，就不該要求依賴

> `--help` 不該需要 SDK；純函式不該被 top-level 的重量級 import 擋住而無法測試。

## F. 兩個 agent 做同一件事（2026-09-16 實測：**沒有好的自動偵測**）

當天兩個 session 各自在 `wiki_ingest.py` 加了「素材沒放進 bucket」的警告 ——
**兩份實作、兩組測試、兩道守門全綠**，只有實跑 ingest 才看到輸出印了兩則。

### 🔴 試過用「訊息文字相似度」偵測，量測後否決

| 量測 | 結果 |
|---|---|
| 門檻 0.85 掃全庫 | 15 對命中，**全是假警報**（同行被算兩次、「缺 --instance 參數」vs「缺 --role 參數」這類） |
| **真實那一對** | 相似度 **0.40** —— 兩人講同一件事但用詞完全不同 |
| 降到 0.60 | 仍抓不到真實那對，而假警報會更多 |

> 💡 判準：**做偵測器之前，先拿「真正踩到的那個案例」餵它。**
> 抓不到就別做 —— 那會變成「名字叫它、卻放它走過去」的守門，
> 比沒有更糟（它會讓人以為這件事有人在管）。

### 實際有效的兩件

1. **事前**：動手加一個能力之前，先看那個檔案**最近的 commit 標題**。
   當天那筆標題就寫著「ingest 對『沒放在 source-id bucket』的素材提醒（不擋）」——
   `git log --oneline -5 -- <file>` 一眼就看得到。
2. **事後**：對「同一個輸入只該出聲一次」的行為寫 `..._exactly_once` 測試
   （範例：`test_bucket_warning_is_emitted_exactly_once`）。
   這條守的不是「誰重複了」，是**輸出不得重複** —— 那是可確定斷言的。

### 實地回饋（2026-09-16，來自另一個工作面）

新加的兩道守門在別人實際操作下的表現 —— **零誤報**：

| 守門 | 觸發 | 判定 |
|---|--:|---|
| `pre-push`（刪 skill 時） | 2 次 | 都是真的（刪 `ark-news-daily` 6 份、刪一支測試），驗證後以 `ARK_ALLOW_STALE_PUSH=1` 放行 |
| `check_consumers` | 報 6 個 | 逐一查上游 git 歷史確認，全部屬實 |

> 💡 這是**別人操作下**的數據，不是我自己跑的 —— 守門的誤報率要由沒寫它的人來驗。

⚠️ 別靠「兩邊守門都綠」推論沒有重複 —— **重複的兩份各自都是對的**，
所以兩邊都綠是這個失敗模式的**正常現象**，不是反證。

## E-5　標籤不等於內容 —— 兩個方向都要防

已上移到 `AGENTS.md`（`## 終端回饋處理`）。這裡留兩個實例，因為它們是**一體兩面**：

| 方向 | 實例（2026-09-16~17，peer 實查） |
|---|---|
| **內容不在，標籤在** | 發 wheel 時版號兩處都是 1.0.17、tag 也在，**解開已發的 wheel 才看到安全修法不在裡面**（那版是兩天前發的，內容是別的） |
| **標籤先跑，內容不在** | 工作區版號被改成 **1.1.0**（兩處），但與 `v1.0.18` tag 逐檔比對**除了版號那行零差異**，無 commit、無 CHANGELOG —— 一個**空版號**，而且是 minor bump（語意上暗示有新功能） |

> 💡 後者的代價比前者晚才發作：一旦有人照它發版，就會產出「1.1.0」但內容等於
> 1.0.18 的 wheel，而 CHANGELOG 裡找不到它 —— 那時已經很難追。
> **內容進去之後再升版號**；真要先升，至少先寫 CHANGELOG 條目，
> 讓「這個版號要裝什麼」有個落點。

## E-4　驗證要印**整段**，不要只印你加的那個鍵

> 實例（peer 2026-09-16）：用腳本往 YAML 插一行，結果**把整個 `server:` 段複製了一次**
> （值相同所以功能無害，但檔案壞了）。抓到它的是驗證那一步**印出整段**；
> 只檢查「`auth: "off"` 在不在」的話完全看不出來。

同型於 E-3：斷言「我要的東西在」不等於「沒有別的東西被弄壞」。
**改檔案的驗證要看改動後的那個區塊長什麼樣，不是只看那個鍵。**

## E-3（留下的那條）　靜默失效的三種長相

sync 印一行「跳過」· 蒸餾掃出零筆 · agent 讀到上游已刪的舊版。
**它們都不會讓任何指標變紅。**
