# ark-agent-cli 2.3 / 2.4 優化計畫

## 0. 一句話

分析報告的結論站得住：prototype 與套件**骨架同構**（分段 + 交接檔 + detach + 判定權不給 agent + 後端抽象），差在 prototype 多了一層**用事故換來的營運治理**。本計畫只吸收那一層裡**與領域無關**的五件事——stdin 餵 prompt、空轉熔斷、崩潰補收尾、用量可視、能力邊界——其餘（機台核帳、SSIM、觸發中心、scrcpy）留在 prototype / ark-mobile-adb，不混進通用工具。

## 1. 對齊現況（以 main 2.2.1 為基準，不是我手上的 build）

| 報告指出的差距 | 2.2.1 現況 | 本計畫 |
|---|---|---|
| prompt 走 argv（Windows 長度雷） | `BACKENDS[*].prompt = "argv"`（kiro / claude / gemini / codex 皆 argv；只有 fake 走 stdin） | **W1 改 stdin**，不支援 stdin 的退回 prompt 檔 |
| 無空轉偵測 | 只有 `segment_timeout` 與段數 / 分鐘預算 | **W2 空轉熔斷**：連 N 段無進展即停 |
| job 死掉無自動補收尾 | `wait` 能看出孤兒並提示 resume；沒有 finalize | **W3 finalize + 孤兒自動收尾 + gc** |
| 無成本可視 | 無 usage | **W2 用量統計**（每段 `.usage.json` + job 累計 + status 顯示） |
| `--trust-all-tools` 全開 | kiro 一律 `--trust-all-tools`；codex 一律 `workspace-write` | **W4 能力邊界**：spawn 宣告 `--access`，各 backend 映射到最小權限旗標 |
| 「已交接不自結束」/ 段超時 +300s 砍 | 段逾時 = subprocess timeout 砍，無「checkpoint 已寫但 CLI 還在跑」的處理 | **W1 kill policy**：Popen + 輪詢 checkpoint，寫完 60s 未退出就砍 |
| detach 用 start_new_session / DETACHED | Windows 未帶 `CREATE_BREAKAWAY_FROM_JOB` | **W1 補旗標**（bot 以 Job Object 管子進程時，worker 才不會被一起殺） |
| 裝置失聯砍 | 無（領域邏輯） | **W5 通用 watchdog hook**：`--watchdog-cmd`，非零 → blocked；裝置判斷寫在 ark-mobile-adb |

不吸收：錄影存留策略（屬 ark-mobile-adb 的 artifacts）、autobox 核帳、觸發中心、額度查詢（codex app-server 專屬；通用層只做「有就記」）。

## 2. 分階段

### W1 — 餵法與進程治理（2.3.0，Breaking：BACKENDS 契約）

| # | 改動 | 位置 | 驗收 |
|---|---|---|---|
| 1 | **stdin 優先**：`BACKENDS` 加 `prompt: stdin` 給 codex（`exec … -`）、claude（`-p` 無參數讀 stdin）、gemini（管線讀 stdin）；kiro 先探 `kiro-cli chat --no-interactive` 是否吃 stdin，否則用 **prompt 檔**：寫 `segments/NNN.prompt.md`，argv 只放一行「讀 `<path>` 並依其執行」 | `agent_common.build_argv` → 回 `(argv, stdin_text, prompt_file)` | 10 KB 與 60 KB prompt 在 fake / 每個 backend 的 `agent_cli.py -b X "…"` 不出 `WinError 206`；單元測試：argv 長度 < 2 KB |
| 2 | **kill policy**：`agent_cli.call_watch(argv, checkpoint_path, grace_s=60, timeout+grace)`：Popen 後每 2 s 看 checkpoint 檔；已寫且 CLI 仍在 → grace 後 kill 並視為成功；逾時 → kill 並視為該段白做 | `agent_cli.py` 新函數；worker 改用 | 測試：fake 寫完 checkpoint 後故意睡 5 s，grace=1 → 段成功且 elapsed < 3 s |
| 3 | Windows detach 加 `CREATE_BREAKAWAY_FROM_JOB (0x01000000)`，失敗（權限不足）退回原旗標 | `agent_spawn.detach` | Windows 實機：bot 進程結束後 worker 仍在 |
| 4 | `pid_alive` 文件化：Windows 走 OpenProcess（2.1.0 已改），禁止 `os.kill(pid, 0)` | `job-contract.md` | — |

### W2 — 空轉熔斷與用量（2.3.0 同版）

| # | 改動 | 驗收 |
|---|---|---|
| 5 | **checkpoint 加兩個欄位**（協定 1 → 1.1，向下相容）：`actions`（本段做了幾個有效動作，整數）、`evidence_new`（本段新增證據數）。worker 計算「進展」= `actions > 0 or evidence_new > 0 or metrics 變動 or progress 文字 ≠ 上段`；**連續 `--idle-segments`（預設 3）段無進展 → 終態 `blocked`，reason=`idle`**，inbox 照發 | 測試：fake `idle=5` 腳本第 4 段起無進展 → 第 6 段後 blocked(idle)；progress 相同但 metrics 變動不算空轉 |
| 6 | 協定段加一條：「每段至少一個有效動作或新證據；連續三段沒有會被熔斷——沒事做就 `done`，做不到就 `blocked`，不要空轉」 | `subagent-protocol.md` |
| 7 | **用量**：從 CLI 輸出抽 usage（claude `--output-format json` 的 `usage`、codex `--json` 的 `turn.completed`、gemini json 的 `stats`；kiro 無則記 `null`）→ `segments/NNN.usage.json`；job.json 累計 `usage.{input_tokens, output_tokens, cost_usd?, llm_calls}`；`status` / `result` / inbox notice 帶出 | 測試：fake 輸出含 usage 區塊 → 累計正確；無 usage 不報錯 |
| 8 | **段預算提示**：prompt 的「本段執行資訊」加「本 job 已用 N 段 / M 分鐘 / X tokens」 | 看 prompt 檔 |

### W3 — 崩潰補收尾、孤兒、回收（2.3.1）

| # | 改動 | 驗收 |
|---|---|---|
| 9 | **`finalize --job`**：對 state=running 但 pid 已死（或 `--force`）的 job：從現有 checkpoints 補 `result.md`、state → `failed(reason=worker_died)`、殺殘留 `child_pid`（exec）、清 `cancel`、發 inbox | 測試：spawn 後直接 kill worker → finalize → result.md 存在、state failed、inbox 有通知 |
| 10 | **孤兒自動收尾**：`status` / `list` / `inbox` 遇到孤兒 job 自動 finalize（可 `--no-auto-finalize`） | 測試同上但不手動 finalize |
| 11 | worker 本身 `try/finally`：任何未捕捉例外都走 finalize 路徑（現在只寫 state=failed 不產 result.md） | 測試：fake `crash` → result.md 存在 |
| 12 | **`gc --days 7 [--keep failed,blocked] [--dry-run]`**：刪舊 job 目錄；artifacts 大小寫進 `list` | 測試：建三個假 job 改 mtime → 只刪到期的 done |

### W4 — 能力邊界（2.4.0）

| # | 改動 | 驗收 |
|---|---|---|
| 13 | spawn 加 `--access read-only | workspace | full`（預設 **read-only**）與 `--allow-tools a,b`；`BACKENDS[*].access` 映射：codex `-s read-only/workspace-write/danger-full-access`、claude `--allowedTools …`（read-only = 只讀工具）、kiro `--trust-tools=<list>`（read-only = 不帶 `--trust-all-tools`；全開才帶）、gemini `--approval-mode default/yolo` | 單元測試：三種 access × 四 backend 的 argv 快照 |
| 14 | task.md frontmatter 可宣告 `access` / `allow_tools`，spawn 以較嚴者為準；協定段第 9 條改為引用這個宣告 | lint：task 宣告 full 但 spawn 給 read-only → 以 read-only 跑並在 events 記 `access_downgraded` |
| 15 | `exec --cmd` 加 `--allow-shell` 顯式開關（預設只允許 python / 腳本白名單），擋住把使用者訊息塞進 shell 的誤用 | 測試：含 `rm -rf` / `;` 的 cmd 不帶 `--allow-shell` → BAD_INPUT |

### W5 — 通用 watchdog 與 aiqa 案例回填（2.4.0 同版）

| # | 改動 | 驗收 |
|---|---|---|
| 16 | spawn 加 `--watchdog-cmd "<cmd>" --watchdog-fail N`：每段開始前跑一次，exit ≠ 0 連 N 次 → `blocked(reason=watchdog)`；aiqa 案例填 `ark_mobile_adb.py doctor` | 測試：watchdog 指令第 2 次起失敗，N=2 → 第 3 段前 blocked |
| 17 | `case-aiqa-steward.md` 與 `examples/tasks/aiqa-steward.md` 改用 `--access read-only --watchdog-cmd doctor --idle-segments 3`；steward 的 checkpoint 填 `actions` / `evidence_new` | fake 全鏈重跑綠 |
| 18 | 與 prototype 的分工寫進 `references/v2-design.md`：通用層（本 skill）= 分段 / 預算 / 回報 / 能力邊界 / 熔斷 / 收尾；領域層（ark-mobile-adb、prototype）= 核帳 / 觸發 / 錄影 / 裝置 | 文件 |

## 3. 放行條件（每階段）

- pytest 全綠（2.2.1 的 20 條不改預期；每個 # 至少一條新測試，含反證）
- `quick_validate` 綠；`audit_skills` 本 skill 零 P1；W1 升 2.3.0 時在版本段寫 Breaking（BACKENDS 回傳三元組、預設 access 改 read-only 是 W4 的 Breaking → 2.4.0）
- Windows 實機各一次：10 KB prompt、bot 結束後 worker 存活、OpenProcess 判活
- aiqa fake 全鏈（demo-slot + fake backend）在 W2 / W5 後各跑一次，不得出現 idle 誤判

## 4. KPI

| 指標 | 2.2.1 | 目標 |
|---|---|---|
| 最長可用 prompt（Windows） | ~8 KB（argv） | ≥ 64 KB（stdin / 檔） |
| 空轉燒 token 上限 | 無上限（到 max_segments） | 3 段 |
| job 死亡後有 result.md | 否 | 100% |
| 每個 job 可見 token / 成本 | 否 | 是（有 usage 的 backend） |
| sub-agent 預設權限 | 全開 | read-only |
| 已交接後多等的時間 | 到 segment_timeout | ≤ 60 s |

## 5. 排序與理由

W1 → W2 先做：stdin 是「我們前面踩過卡住」的現場問題；空轉熔斷是 prototype 用 8000 萬 token 換來的教訓，兩者都是幾十行。W3 讓失敗可觀測。W4 改預設權限是行為變更，放後面並升 major-ish（2.4.0）。W5 把 aiqa 案例收攏。不做「把 prototype 搬進來」——它的價值在領域，通用層只借治理。

## 6. 給墨驗的回信要點

分析正確且可直接當 W1–W5 的來源；兩處補充：(1) 2.1.0 起 `_alive()` 已是 OpenProcess，與 prototype 的 `pid_alive` 同解；(2) 「選角路由」在 2.1.0 已落地（`roster` + `--route`），prototype 若要多專家可直接複用 agents.yaml 契約，不需另造。
